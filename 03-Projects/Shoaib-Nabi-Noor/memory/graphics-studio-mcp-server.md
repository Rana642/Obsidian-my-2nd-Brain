Two intake mechanisms feeding the same `{base64, mimeType}[]` shape into `runGenerationBatch`: the web form (`components/PromptGenerateForm.tsx`) reads files client-side via `FileReader`+base64 (browser has no filesystem access); the MCP tool takes `referenceImagePaths: string[]` (local file paths) and reads+base64-encodes them server-side via `node:fs/promises` — chosen over having the agent pass base64 directly, since a human types file paths naturally but an agent computing/passing a giant base64 string as a tool argument would bloat the conversation. Hit one cross-tsconfig type quirk worth remembering: `new Blob([someBuffer], ...)` failed to typecheck under `mcp/tsconfig.json` (Buffer's `ArrayBufferLike` includes `SharedArrayBuffer`, which `BlobPart` rejects) even though the identical pattern in `lib/image-providers/gptImage.ts` passes fine under the root tsconfig — some lib/target combos surface it, some don't. Fix: wrap in `Uint8Array.from(buffer)` instead of passing the Buffer directly to `new Blob([...])`.

It reuses the app's real `lib/` business logic (Supabase service-role client, image providers, placement specs) rather than duplicating it — only the Next.js-only glue (cookie auth, server actions, revalidatePath) is skipped since a standalone stdio process has no HTTP request context.

Key implementation snag: `lib/` files do `import "server-only"`, and that package throws unconditionally under plain Node unless the `react-server` export condition is active (Next.js sets this internally; a bare script must be told). Fix: run via `tsx --conditions=react-server mcp/index.ts` — confirmed by direct testing that this is what makes the import a no-op instead of a crash.

Also extracted `buildImagePrompt`/`buildFooterLine` out of `app/api/generate/route.ts` into a new `lib/prompt.ts` so the web route and the MCP tool share one implementation instead of duplicating the prompt-building logic.

**Why:** Shoaib's own stated use case is pulling finished graphics into *other* website projects' `public/images` folders — meaning he wants this callable from any Claude Code session, not just one scoped to the graphics-studio repo.

**How to apply:** Registration is `--scope user` (see graphics-studio/README.md "MCP server" section for the exact `claude mcp add` command) — global across all Claude Code sessions on the machine, not project-scoped. I could not run `claude mcp add` myself in that session (the `claude` binary wasn't on PATH in that sandboxed shell) — Shoaib needs to run the registration command himself once. If asked to touch this server again, remember `mcp/tsconfig.json` is a separate, deliberately isolated tsconfig (target ES2022/NodeNext/dom lib) excluded from the root `tsconfig.json` so the MCP code doesn't get pulled into Next.js's build-time typecheck.
