Built 2026-09-14, Shoaib's idea: a Windsor.ai-style credential store he'll later put an MCP server on top of (running via Claude Desktop / a web-hosted MCP) so the whole system — Google Ads, Meta Marketing API, GA4, GTM, GSC, and eventually GBP — can be managed from one place. He already has Google Ads (Basic access approved) and Meta Marketing API credentials in day-to-day use via Claude Desktop; this vault is where those (and the rest) now live.

**Deliberately separate from [[adsbyshoaib-vault]]** (the zero-knowledge client-password vault) — Shoaib was explicit about this ("api vault alag password alag"). That vault needs a master password unlocked in the browser; an unattended MCP server could never read it. This one follows the social poster's pattern instead: `client_social_accounts.access_token_encrypted` → same idea, new table.

**Architecture:**
- `api_credentials` table: `service`, `label`, `fields` (jsonb — plaintext field NAMES as keys, e.g. `developer_token`, `client_id`; each VALUE individually AES-256-GCM encrypted before storage), `notes`, `is_active`.
- `lib/api-vault-crypto.ts` — same shape as `lib/social-crypto.ts`, own key `API_VAULT_ENCRYPTION_KEY` (deliberately separate from `SOCIAL_TOKENS_ENCRYPTION_KEY` so rotating one never touches the other). Generated and added to `.env.local` 2026-09-14.
- **Still needs `API_VAULT_ENCRYPTION_KEY` added to Vercel + redeploy** — the production app can't encrypt/decrypt without it (same "missing env var" trap as `SOCIAL_TOKENS_ENCRYPTION_KEY`/`CRON_SECRET` before it, see [[adsbyshoaib-social-poster]]). Not yet done as of this writing.
- List view (`listCredentials()`) never sends field values (not even ciphertext) to the client — only field *names*. Actual values are decrypted only on demand via `revealCredential(id)`, called when the user clicks "Reveal" on one specific entry.
- Service presets (`API_SERVICE_PRESETS` in `lib/dashboard/types.ts`) suggest field names per service (Google Ads: developer_token/client_id/client_secret/refresh_token/customer_id; Meta Marketing: app_id/app_secret/access_token/ad_account_id; GA4/GTM/GSC/GMB: client_id/client_secret/refresh_token + a service-specific id) — purely a UX convenience, any field can still be added/removed freely, including a "custom" service.
- Sidebar: renamed the old "Vault" entry to **"Password Vault"** for clarity now that there are two, added **"API Vault"** (Plug icon) right below it.

**New reusable infra — `scripts/run-sql.mjs` + `SUPABASE_DB_URL`:** Shoaib gave a direct Postgres connection string (Supabase pooler) specifically so future schema changes don't need him to open the Supabase SQL Editor by hand each time (a recurring friction point — see the process lesson in [[graphics-studio-project]]). Stored in `.env.local` only (never committed, never echoed to any output/log). `npm run db:sql -- -c "<sql>"` or `npm run db:sql -- path/to/file.sql` runs it directly against live Postgres via the `pg` package (added as a devDependency). **`SUPABASE_DB_URL` is a local/dev-only credential — it must NOT be added to Vercel**, since nothing in the deployed app reads it; only this session's ad-hoc migration script uses it.

**Verified end-to-end (2026-09-14)** against live Supabase: created the `api_credentials` table via `scripts/run-sql.mjs`, then a temporary Supabase Auth admin user (created via Admin API, deleted immediately after — same pattern as [[graphics-studio-project]]'s Phase 1 test) to sign into the real dashboard login form and confirm add → reveal → edit (preloads real decrypted values) → delete all work correctly with the real encryption key.

**Critical gotcha, already hit and fixed — read this before generating any more Google refresh tokens for this project:** while the OAuth consent screen ("Google Auth Platform") is in **Testing** publishing status, every refresh token issued expires in exactly 7 days (`refresh_token_expires_in: 604799` in the token response) — regardless of scope. **Fixed by publishing the app to "In production"** (Audience page → Publish app → Confirm) — required filling in the Branding page's App domain fields first (Application home page `https://adsbyshoaib.com`, privacy policy link `https://adsbyshoaib.com/privacy`, plus adding `adsbyshoaib.com` as an Authorized domain; app logo was deliberately left blank — uploading one forces mandatory verification even outside Testing). Sensitive scopes (analytics.readonly, tagmanager.*, webmasters.*) did NOT block publishing or trigger an immediate verification wall for this single-developer-as-sole-user setup — Google's dialog only warns verification *may* eventually be required. **Any refresh token obtained via OAuth Playground before this publish has the 7-day cap baked in permanently** (publishing afterward doesn't retroactively fix an already-issued token) — the GA4 refresh token was regenerated once for this exact reason; the GTM/GSC one was generated after publishing, so it was correct on the first try.
