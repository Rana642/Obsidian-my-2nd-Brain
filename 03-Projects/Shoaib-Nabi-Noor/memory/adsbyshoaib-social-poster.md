**Rate-limit/spam-policy safety pass (2026-09-13):** researched Meta's actual docs rather than guessing. Instagram Content Publishing API hard-caps at **100 posts/24h per account** (50 for carousels) — added `assertInstagramPublishingHeadroom` in `lib/social-fb.ts` (checks `/​{ig-id}/content_publishing_limit` before every IG publish, fails with a clear message instead of a confusing Graph error). **Native Facebook scheduling added, same day.** Shoaib pasted external research (from another AI chat) about bulk-posting suspension risk and asked to verify + implement best practices — most of it was generic/outdated (e.g. "200 calls/hour" is the old Platform rate limit, superseded by the Business Use Case formula I'd already found), but one suggestion was real and verified via Meta's docs + community sources: Facebook's `/photos` endpoint accepts `published=false` + `scheduled_publish_time` (window: **10 min to 30 days ahead**) — Meta's own servers then fire the actual publish, which reads as native scheduling (like a person using Business Suite) rather than an app "pushing" a post at the last second. Instagram has **no equivalent at all** — confirmed no third-party tool (Buffer, Metricool included) can do this for IG; it's always held and fired by the tool's own scheduler at the right time, which is what our cron already does.

Implementation (`lib/social-post.ts` is now the orchestration layer, not just cron): `submitNativeScheduleForPost(postId)` fires as soon as a post gets captioned — either from the dashboard (`createPlannerPost` action, if a caption was typed at upload time) or from the MCP tool `social_set_caption_and_schedule` — and hands eligible Facebook accounts straight to Meta's scheduler, recording the result under `scheduled_posts.result.native` while `status` stays `'scheduled'`. The cron (`app/api/social/cron/route.ts`) reads that `result.native` on each due post, excludes already-natively-handled accounts from its own live-publish call (`postToAllProjectAccounts`'s new `excludeExternalIds` param), and merges both result sets — so a Facebook-only project may already be fully "posted" by the time cron even looks at it (Meta published it on its own), while Instagram on the same post still goes through the live call as before. Dragging a post to a new day (`movePost` → `rescheduleNativePosts`) deletes the stale Meta-side draft and resubmits for the new time, to avoid a duplicate post if it was already natively scheduled for the old date.

Also added response-header usage monitoring: `peakUsagePercent()` in `lib/social-fb.ts` parses whichever of `x-business-use-case-usage` / `x-page-usage` / `x-app-usage` Meta attaches, and the cron backs off (stops processing further due posts, leaves them for the next 15-min run) if any call reports ≥90% of the rolling rate-limit window used.

None of this is remotely close to mattering at Shoaib's actual volume — it's insurance against a page ever getting flagged, done properly (verified against Meta's docs) rather than cargo-culted from someone else's AI chat. **Reminder for later:** Shoaib wants to eventually turn this into a "SociallySnap"-branded SaaS ("Powered by Ads by Shoaib") — see the deferred-decision note further up this file; nothing about that has started, this was all still the internal-tool build.

**Two real architectural differences from Meta/LinkedIn, both handled:**
1. **Publishing is async.** TikTok's init call returns a `publish_id`, not an immediate result — `publishTikTokPhotoPost` does a bounded poll (5× every 2.5s) against `/v2/post/publish/status/fetch/` and returns whatever status it lands on; still-`PROCESSING` after that budget is treated as accepted-not-failed (same trust-the-platform stance already taken for Facebook's native scheduling, which is also never followed up on afterward).
2. **PULL_FROM_URL needs a verified domain.** TikTok checks the image URL's domain against ones verified in the Developer Portal — only `adsbyshoaib.com` is verified (done earlier for exactly this), not R2's own bucket/gateway domain that `presignDownload()` produces for Meta. **Two real Instagram bugs found + fixed same day (2026-09-16), caught because Shoaib asked to check that day's live Hotel Silver Sand/Hotel Elegant posts rather than assuming success:**
1. **Race condition** (commit `0fa45d4`): `postInstagramPhoto` in `lib/social-fb.ts` called `media_publish` immediately after `media` container creation, with no wait for Meta to finish processing it — intermittently fails with `"Media ID is not available"`. Fixed with `waitForContainerFinished()`, polling `GET /{container-id}?fields=status_code` (1.5s interval, ~20 attempts) until `FINISHED`, failing fast on `ERROR`/`EXPIRED`.
2. **PNG outright rejected** (commit `6ace201`): once the race was fixed, the retry immediately hit a second, separate error — `"Only photo or video can be accepted as media type"` — because Instagram's media-container creation rejects PNG via `image_url`, unlike Facebook's `/photos` endpoint which accepts PNG fine (confirmed live: same image posted to Facebook succeeded, only the Instagram side failed both times). Fixed the same way TikTok's PNG rejection was fixed: a new `app/api/social/instagram-media/[token]/route.ts` (mirrors `tiktok-media`, same short-lived-token pattern via new `lib/social-instagram-media.ts`) always re-encodes to JPEG via sharp (flatten alpha to white, no resize/letterbox needed — Instagram auto-crops out-of-range aspect ratios itself). `postToOneAccount` in `lib/social-post.ts` now calls `mintInstagramMediaUrl(mediaKey)` for the Instagram branch instead of passing through the raw R2 `imageUrl`.

**Net effect: Facebook posting was never actually the risky path for image format — Instagram and TikTok both need JPEG, Facebook doesn't care.** If a future platform integration is added, check its docs for format support explicitly rather than assuming "if Facebook accepted it, everyone will."
