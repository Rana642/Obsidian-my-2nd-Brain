**Design decision**: every one of these APIs has a huge, evolving object model (Google Ads alone has 190+ mutable resource types) — so instead of hand-wrapping every field/resource (which would always be incomplete), each service got a **generic passthrough** onto its real REST shape (GAQL for Ads, path/method/body for the Google Admin-style APIs and Graph API). The calling assistant is expected to know or look up the target API's request shape; the tool just handles vault-credential auth + the HTTP call.

**Safety layering**: read-only calls (search, GET) always execute directly. Every write call (mutate, non-GET passthrough) requires `confirm: true` in the tool args, or it returns a preview of exactly what would be sent without sending it (Google Ads additionally gets a real server-side `validateOnly` dry-run). This sits on top of Claude.ai/Claude Code's own per-tool approval gate (visible in the connector's "Tool permissions" UI, currently all set to "Needs approval") — two independent layers before any live ad spend, campaign change, or GTM publish (which pushes tags to a real production site) can happen.

**Credentials**: all read from the same `api_credentials` vault (`lib/marketing-vault.ts`'s `getVaultCredential(service)`) that `/dashboard/api-vault` manages — services `google_ads` (client_id/client_secret/refresh_token/developer_token), `meta_marketing` (app_id/app_secret/access_token), `ga4`/`gsc`/`gtm` (client_id/client_secret/refresh_token, same Google installed-app OAuth pattern via `lib/google-oauth-token.ts`). None of these vault rows store a specific customerId/ad-account-id/property-id — those are passed as tool arguments each call (use `google_ads_list_accounts`/`meta_ads_list_accounts` first to discover them).
